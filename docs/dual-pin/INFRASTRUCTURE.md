# AccessModeCore integration contract

Status: stage-2 foundation verified, with partial stage-3 PIN/AppLock/account/root adapters and verified startup/runtime checkpoints. Native setup/enrollment/management and history/notification integration remain incomplete. This is not yet a usable Dual PIN application.

## Authentication and configuration

Peer identity preserves the exact account, namespace and signed ID. Upstream
`Postbox/Sources/Peer.swift` restores namespace 3 through `Int32(bitPattern:)`, and
`TelegramCore/Sources/State/UpdatesApiUtils.swift` converts the API encrypted-chat
ID directly to Int64. Secret chat IDs therefore accept exact nonzero signed Int32
values, including negative ones, without `abs` or packed-ID conversion. Cloud
namespaces 0/1/2 retain positive IDs; secret overflow and unknown namespaces deny
access. New signed-secret settings are readable by this validator; an older fork
with the positive-only validator will refuse those settings and must not reset or
fall back to raw accounts. Native routes and real secret-history adapters still
need integration; this identity validation does not supply a message boundary.

`AccessCredentialStore.initialize` is initial-only. Its synchronous `prepareProtectedResources` hook runs under the initial-only file lock after config/PIN validation and proof construction but before vault publication. Existing owner authentication and preserved legacy resource keys are mandatory in the product adapter. Missing/corrupt/unsupported existing state cannot be reset by initialization. `isConfigured` returns false only when both the vault and its committed-state witness are confirmed absent; invalid/unsupported state, a missing previously witnessed vault or unavailable Keychain throws. There is no biometric/recovery API. Use the fork's own bundle/App Group namespace and Keychain service, never another application's production store.

Both six-digit ASCII PIN records are checked for each normal candidate. Verification failure commits the applicable independent budgets before returning; a valid B clears only B's budget. A reboot with a blocked budget starts another full 60-second delay. Grants leave the store only after the successful atomic commit; they are not Codable and have no public initializer. Changing a PIN requires its current code and invalidates prior grants.

The encrypted file uses AES-GCM with schema, namespace and envelope revision in its authenticated context, a non-synchronizing `WhenUnlockedThisDeviceOnly` Keychain key, 0600 files, a 0700 directory, backup exclusion, interprocess `flock`, atomic rename and fsync. Authenticated envelopes do not provide hardware-backed anti-rollback protection against restoration of an entire old encrypted vault with its original key. Raw Telegram databases remain outside this module's PIN encryption boundary.

Each encrypted-state namespace also has an irreversible Keychain presence witness under the same service/access group. It contains only the bound namespace, no PIN, account identities or messages. The provider must distinguish confirmed absence from protected-data/query failure; malformed existing witnesses cannot be overwritten. The witness has the same device-only, non-synchronizing protection as the key. First file commit is followed by witness publication before any receipt/grant/send result leaves storage. Failure before file commit leaves initial setup retryable; failure after file commit denies return and later reads retry witness publication against the intact authenticated file, never owner reinitialization. Existing pre-witness files migrate on a successful read before state is returned.

The independent transcript namespace may initialize once, even when the credential witness exists, but loss of its committed file cannot reset the boundary/provenance ledger or register an already enqueued send again. There is no automatic reset/recovery API. Reinstalling the same bundle can retain Keychain witnesses while removing files: that state remains denied rather than reopening raw accounts. An owner recovery/migration process is still a release prerequisite. Complete deletion/rollback of both files and Keychain state, loss before witness publication, and pre-upgrade loss before migration are not cryptographically detectable by this mechanism. It does not provide independent database encryption or a backup restoration guarantee.

Apple documents unlocked-only access for [`WhenUnlockedThisDeviceOnly`](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly). Apple's [DTS explanation of uninstall behavior](https://developer.apple.com/forums/thread/36442) explicitly treats Keychain survival as an implementation detail, so this witness is not a promise of persistence across uninstall or device migration. Missing-state verification passed 106 Mac and 108 hosted iOS Core cases plus 17 hosted legacy/actual-AccountManager cases. The hosted Keychain test verifies separate namespaces, device-only/non-synchronizing attributes, reopen and refusal to overwrite malformed witnesses; no physical-device Keychain guarantee is inferred.

Keep credential verification/file transactions off the main thread. File-backed policy validation belongs at query delivery/navigation/send boundaries, not once per displayed row. Do not retain an `AccessModePolicy` outside its coordinator callback and treat it as authorization for later work. Capture an opaque ticket and revalidate on every async delivery/side effect. The callback is synchronous; UI lifecycle and cross-process revocation notification wiring are still required in stages 3 and 5.

`AccessModeCoordinator` starts locked. UI code must install an opaque cover before locking/unlocking, prepare a fresh permitted root using the preparation ticket, then complete preparation before active operations. A late result from an old ticket does not invalidate the new preparation. A storage failure invalidates the current local presentation. A main-app lock persistently revokes grants; an extension's own unlock does not unlock/revoke the main UI.

At PIN submission call `preparePINRequest` synchronously before dispatch, then `beginUnlock(pin:request:)` off the main thread. The single-use request binds the exact coordinator/generation; a later lock makes queued work unable to begin. Cancel a discarded result using `cancelPreparation(ticket)`: stale tickets have no effect, the current preparation locks, an active ticket cannot be cancelled through this API. `cooldownRemaining` exposes only the neutral shortest all-blocked cooldown, no role label/budget.

The optional `ModePINEntryAuthentication` hook in PasscodeUI follows this contract and never issues a legacy protected-resource session. Its preparation callback must validate/build the root; there is no automatic app unlock. AppLock installs this hook for an existing configured vault and refuses legacy unlock callbacks until its supplied root validator succeeds. Its held cover is released explicitly after preparation, so unrelated presentation updates cannot remove it early. An unavailable-vault requirement forces a denied synthetic six-digit reference rather than falling back to an unsecured/legacy challenge. Native setup still does not publish a vault, and B admission is explicitly denied until the remaining data/external adapters pass verification. The actual PIN node uses a stock theme/built-in wallpaper in both initial and updated presentation/keyboard data.

Configuration validates one shared primary, exact installation/environment/record/self-user identities, unique server accounts, role-local selection and visible-only Premium limits. Hidden chats belong to the shared primary. Each hidden chat has a persistent generation: unhide removes it; rehide creates a new one. No role UI may consume the complete raw registry.

## Stage-3 management commands

`coordinator.setHidden` and `selectAccount` replace authority only after the encrypted mutation commits. Their new ticket is preparing: attach the opaque cover first, discard the old query/navigation epoch, prepare the new revision/root, then complete preparation. Old tickets and cross-process old configuration grants are invalid. Hidden-management data is A-only; selection returns only the current role's account identity.

`AccessChatVisibilityAction` is a non-Codable menu command bound to an exact ready
root. Its hidden-status field is presentation only. Creation/execution require
the main application and current A management policy; inactive execution locks
before any configuration write. Old/foreign/replayed commands refuse before
disturbing a newer root. The native shared-context bridge additionally binds the
exact selected loaded account context and root preparation; the chat menu adds
the local action only at final main-thread delivery. The successful command uses
the existing covered mutation/fresh-root path. Six new cases passed within 127
Mac / 129 hosted Core cases. Full native compilation and configured menu checks
are recorded separately in `PLANS.md` and `CHAT_MANAGEMENT_MANUAL_CHECKS.md`.

Enrollment is explicitly staged: `beginEnrollment` commits the role/flow origin before creating or exposing authorization UI; `bindEnrollment` durably binds its newly created provisional record; only `completeEnrollment` may adopt the confirmed self-user identity of that exact record. Grants, flow issuer, configuration/revocation and provisional record must all match. The permit is not Codable. An existing visible identity returns its permitted existing identity; an other-role collision returns only `unavailable`. The adapter must neutralize its own provisional session, never an existing raw account. Reusing a permit, another record, installation, issuer or revoked flow fails closed.

Lock/configuration/PIN changes abandon pending authority. Unknown crash-created records remain quarantined rather than adopted into the next mode. This foundation does not implement provisional-session cleanup, restart recovery UI, live Premium refresh or Telegram's enrollment callbacks; those adapters remain stage-3 work. The dormant native account projection exists as described below. A hidden role's Premium membership cannot increase the other role's enrollment allowance.

## Native root/account presentation contract

`policy.projectAccounts` accepts observed record/environment/cloud-self-user identities. It preserves the order of matching visible accounts, excludes unknown/reused/wrong-namespace identities and denies ambiguous record/server duplicates. A missing selected account yields no primary; it never adopts the first raw/visible row.

`AccessRootPresentation` owns a separate opaque root token. Its mandatory main-thread callbacks cover synchronously, discard old presentation, publish a ready root and finally remove the cover. PIN authentication alone cannot complete it: the exact prepared account, current generation, active application and durable grant must all match. Initial/lock I/O errors still leave a covered detached local root. An old completion/cancellation cannot disturb a newer preparation. A callback that locks or switches during ready publication cannot subsequently uncover its older root. `hideCover` may throw only before uncovering; failure must preserve the barrier and the driver discards/revokes the root.

Use the driver's `selectAccount`/`setHidden` for native mutations: after a permitted preflight they detach local authority and cover/discard before storage mutation, then return a fresh root token. Denied other-role IDs/B hide actions leave the current permitted root intact. `canManageChatVisibility` and `isMarkedHidden` are A-only and apply to supported shared-account chats.

`SharedAccountContextImpl` retains private raw contexts for normal account/network processing. Its startup mode requirement is set before raw record subscriptions and automatic authorization. Public context/info emissions are revalidated on the main thread against current authority, including already queued old emissions; unauthenticated/preparing/unavailable states publish nothing. The root gets a separate preparation stream and validates exact context identity before construction/readiness. Native account switching persists role selection and drops reuse of old settings/chat controllers. While the enrollment adapter is absent, configured-mode authorization remains closed; the upstream automatic/duplicate-removal fallback cannot create or transfer a raw record. No B root is enabled.

`AccessRuntimeBootstrap` permits ordinary initial setup only after a successful absent-vault check. Factory, Keychain, corrupted/unsupported-file and protected-data failures require mode authentication. The main runtime uses its own bundle/App Group namespace, installs unavailable requirements before raw UI publication, synchronously detaches the root before blocking I/O and retains the native cover while old sheets are dismissed. `AppDelegate` carries the root token through the authorized-context pipeline, validates again after native dismissal, and checks it before mounting/completing readiness. Root admission is checked during preparation, before ready publication and before uncovering; the incomplete B integration is denied at that boundary. All account factory/navigation/send/async renderer boundaries still require the stage-4 audit. Hosted core tests use isolated UI callbacks; they do not prove native authenticated frame secrecy or account authorization.

The additional presentation integration cancels pending readiness/timeout requests and discards attached window/global overlays and portals. It retains only AppLock's exact current lock controller. Revoked requests cannot attach a view or run their old completion; reentrant teardown during ready publication is guarded. The mode window also checks current permission at presentation and readiness delivery; global/native/portal presentation is denied while inactive, locked, preparing or natively covered. This boundary does not replace account/chat/renderer-specific stage-4 checks. Thirteen hosted UI cases passed, including actual Display presentation contexts; the additional wiring passed a full simulator app build.

`PasscodeCredentialStore.requireModePINManagement` is a process latch installed before AccountManager initialization whenever a mode vault is configured or unavailable. It denies generic legacy-only PIN replacement/removal/migration/destructive reset and biometric enable/authentication. PIN-authenticated resource reads and authorized cleanup remain available. Six hosted migration/management cases passed, including denial without changing either mode credential or the protected resource key; full application compilation passed. The own-PIN settings adapter described below is being verified separately. An unavailable state cannot be reset through those generic APIs.

Own-PIN work uses an opaque single-use `AccessPINChangeRequest`. Main-thread preparation covers and detaches the root before replacing persistent authority. Its temporary capability is restricted to PIN replacement; configuration reads, visibility changes and ordinary data authority are denied. Worker execution verifies its generation, consumes it, verifies the own current PIN through the A journal or B replacement, and finishes locked. Background cancellation, duplicate completion, I/O failure and stale/reentrant work cannot reopen an old root. PINs are not included in the request or persisted as plaintext.

The generic own-PIN form accepts six ASCII digits and a matching new-code confirmation. It clears all fields and consumes its callback before invoking the trusted adapter, and invalidates on inactivity or removal from its window. Inputs use secure numeric fields with no advertised autofill content type; this is not a guarantee against all system/password-manager suggestions. The AppDelegate factory binds the form to the exact opaque root token, account context, coordinator and fresh policy. Central SettingsUI entrypoints recheck mode requirements, including delayed legacy delivery, and lock if the required factory is unavailable. Backend failure also finishes locked, with pending A changes retained for recovery. No other PIN, role label, biometric/disable-PIN/timeout option or automatic unlock is exposed. Nineteen hosted UI cases passed; configured native form flows and physical-device behavior still require dedicated verification.

Pending owner-journal recovery has a separate opaque generation and no account/data grant. AppDelegate retries existing configured state after foreground/protected-data availability, stays covered during worker recovery and leaves the coordinator locked afterward. An unavailable factory never clears requirements, even if a later inspection reports absence. Native configured/pending-journal startup and physical frame guarantees still require dedicated validation.

`commitDualPINLegacyReference` runs off-main and waits at most five seconds for AccountManager's committed transaction with exact reference readback. Silent refusal or timeout prevents journal finalization; late publication is reconciled on idempotent retry. Sixteen hosted legacy/migration/reference cases passed, including reopening actual AccountManager metadata with no resolver fallback and preserving denied recovery after a blocked publication. The initial red fixture crash was an incorrect missing-state initialization flag, corrected only in a verified-new UUID test directory; the read-only reopen cannot repair the database.

## Initial legacy-owner migration

`PasscodeCore.DualPINLegacyMigration.install` is main-process only. Existing protection requires a current PIN-authenticated legacy `.settings` session; absent, resource-scoped, biometric or revoked sessions cannot authorize migration. Initial setup with no legacy PIN can use nil. It rewrites only the PIN wrapping around the existing resource key, preserves protected resources, creates six-digit A protection, publishes the committed legacy reference to the caller, and removes biometric tokens before publishing Dual PIN.

After actual owner validation, initial migration latches generic legacy PIN/protection management off before its first write. Only module-private six-digit owner-update/protection-enable helpers support that initial path; they still require current settings authority for an existing credential and cannot grant account access. Generic PIN replacement/removal/reset/migration/biometric enable and protection toggles are denied across reference acknowledgment, cleanup and Core publication. No legacy file lock spans the AccountManager callback. The process latch remains after an authenticated partial failure: if the first write failed, retry uses the preserved old owner PIN; after rewrap it uses the known new A PIN. A fresh process with confirmed absent Core state can resume ordinary owner management; configured or unavailable Core state reestablishes the persistent startup requirement. Twenty-five hosted legacy cases verify these paths, resource-key preservation, actual metadata acknowledgment and private-helper scope refusal. Native covered retry UI remains pending.

The caller must persist `didCommitLegacyReference` to AccountManager even if the later access-file commit fails. There is no cross-store atomic transaction: if legacy rewrap commits first but file/cleanup fails, Dual PIN remains absent, B is unavailable, and the known new A code unlocks the preserved legacy resources. Read the managed reference on restart; never restore an unsecured challenge or claim failure left the old PIN unchanged. Present a clear retry path. AccountManager delivery, interrupted setup UI and A-change synchronization are not yet wired/verified; an A PIN change must not use `AccessCredentialStore.changePIN` alone while legacy protected resources depend on A.

The hosted `//submodules/PasscodeCore:DualPINMigrationTests` target exercises the actual legacy credential crypto and resource derivation against isolated fake storage: initial setup, 4-to-6 owner migration, missing/revoked/wrong-scope owner, extension/existing-vault refusal, file commit failure, biometric cleanup failure/retry, and B's inability to obtain the A legacy resource session. It does not establish physical Keychain/App Group sharing. Run it through the same Make test command below with that target.

## Transcript adapter contract

- Only an explicit permitted B route calls `RestrictedTranscriptStore.begin`. Discovery, counters and incoming updates must not create a projection. Lists can include an activated projection using its filtered data, never the original raw dialog's preview/count.
- Obtain `TranscriptBoundary` from authoritative synchronization. Cloud peers use namespace 0; the namespace-2 secret-input contract still requires verification against the actual secret-chat engine. A timestamp from a currently loaded page is insufficient. Offline begin has no boundary and cannot admit incoming history.
- Admit only actual incoming messages with exact namespaced IDs after the boundary. Old edits, A/unknown outgoing, old replies, pins, album parts, keyboards and media must never be resolved from raw history to bypass this set. Content renderers and ancillary-data filtering are stage-4 work.
- Generate/persist a stable random ID and local ID; call `recordOutgoing` before engine enqueue. Enqueue only for `.recorded`; `.alreadyRecorded` requires reconciling the existing queue, without duplicate enqueue. The adapter must reconcile engine queue state after crashes and use the same random ID for any authorized retry.
- `acknowledge` and `applyDeletion` are trusted raw-service operations independent of UI unlock. They cannot create a B origin from an unknown outgoing message. The adapter must verify exact account/peer/random/local/server identity before calling them. ACK processing must be coordinated with the actual Postbox message replacement.
- Pass trusted server-adjusted time where available. The persisted high-water time prevents expired entries from reviving on ordinary clock rollback. This cannot prove correct elapsed time under a manipulated offline clock.
- The metadata ledger retains send provenance and tombstones; it does not delete raw/server messages. Its initial encrypted-file backend has a 4-MiB envelope cap and fails closed on overflow. Stage 4 must measure realistic transcript volumes and establish bounded compaction/engine reconciliation or a scalable backend before release. The foundation is not a completed performance guarantee.

## Initial setup commit and lifecycle

`AccessCredentialStore.initialize` returns an opaque `AccessInitialSetupReceipt` only after the encrypted initial file commit. It contains no PIN or account/data authority. `finishInitialSetup` binds completion to the exact store instance, installation, configuration and credential identities and original revocation; completion revokes initial authority and requires fresh PIN entry. A stale, foreign or repeated receipt cannot recreate a missing vault or disturb a newer authenticated state.

`AccessInitialSetupCoordinator` admits only main-app, single-use requests, rejects configured/corrupt state before invoking legacy-owner work, and checks cancellation/reentrancy before receipt completion. The native adapter must cover/detach before preparation and execute crypto/AccountManager work off-main. `DualPINLegacyMigration.installForSetup` supplies the receipt after owner verification, resource-key-preserving rewrap, durable reference acknowledgment and biometric cleanup. No native enablement UI is connected at this checkpoint.

A legacy PIN can exist with resource protection disabled. Initial migration explicitly enables that protection, using the new verified settings session and preserving the resource key, before it publishes Dual PIN. Reference acknowledgment precedes this step so an enable-write failure still leaves a reconcilable known-new-A PIN. Such failure publishes no Dual PIN/B grant and must be retried with fresh owner authentication; an unprotected challenge is never substituted. The clean regression first produced two expected failures in 18 cases; the fixed 19-case hosted suite also verifies failure after rewrap/reference publication and successful known-new-A retry.

`AccessConfiguration.initial` requires independent non-logged-out AccountManager record metadata, explicit pending-authorization status, and the exact chosen shared observation within a complete pool of cloud-self observations. Record IDs and environments must match exactly across the metadata and loaded pool; missing, ghost, duplicate or wrong-environment rows and pending login refuse initialization. The public loaded-array-only shortcut is removed. The builder preserves signed record IDs, self-user identity and loaded display order, assigns all other existing records to A, and validates visible Premium limits. This is a value builder, not evidence that arbitrary observations are authorized. The native adapter must obtain the metadata independently, confirm every actual self peer and revalidate before owner work; names, phone numbers and array indices are not identity proof. The original four pool cases and three completeness cases passed within 113 Mac Core cases; hosted verification is recorded in `PLANS.md`.

`SharedAccountContextImpl.initialModeAccountPool` now supplies that snapshot: main-thread delivery of actual self-info, exact loaded account-instance/record/self-peer matching, real self-user Premium metadata, and an independent synchronous AccountManager record view. Pending authorization and unresolved peers deny. Configured or unavailable mode access clears its initial-only raw cache and refuses the accessor. The native enabling route must capture and then revalidate this snapshot with the same installation/shared record; that route is still absent. Startup and runtime installation both install the same current-lock/fresh-root presentation guard before invalidating legacy sessions/raw streams. Full app compilation and absent/corrupt/restored isolated startup passed; these do not verify a configured picker, live account changes or authenticated native mode transitions.

`InitialPINSetupForm` is an unconnected UIKit input component. Both new PINs are confirmed, must be distinct six-digit ASCII strings, and are cleared before a single-use callback. An existing legacy owner input may be four-digit or alphanumeric; the view requires it but does not authenticate it. All fields are secure and advertise no autofill content type; inactivity/window removal clears them and the callback. Six new cases passed within the 25-case hosted UI suite. Native old-owner verification, shared-account selection, enabling route, covering/detachment and partial-commit retry remain required before exposing initial setup. No B root can be admitted at this checkpoint.

`InitialPINSetupView` composes that form with an account menu keyed by exact signed record ID. Equal display names do not change the submitted identity; empty/duplicate pools and unlisted selections refuse. The view clears the menu, label, selected record, PINs and handlers before a single-use callback and on inactivity/window removal. Five additional cases passed in the 30-case hosted UI suite. `InitialPINSetupController` supplies the native theme/navigation wrapper and revalidates its supplied current-context predicate before display/submission. Neither component grants authority. Full app compilation passed; native factory, fresh owner verification, covered execution/outcome reconciliation and the settings entry remain pending.

The actual-AccountManager integration case migrates a four-digit owner PIN to six digits while preserving the protected-resource key; B cannot obtain the A legacy resource session. The later 19-case hosted legacy suite also checks disabled protection and partial-commit retry. Missing-state denial now uses the durable Keychain presence witness described below. ## Owner PIN A change journal

`AccessCredentialStore.beginOwnerPINChange` requires a current A grant and current A PIN; the replacement must differ from B. Under the encrypted vault lock it prepares the new A proof and an authenticated resource-rewrap plan, then durably stages both before changing the legacy record. Preparation must not write that record. This promotes the vault state to schema 2 at the same `access-state.v1.enc` path; older schema-1 readers reject it, including after completion. Version 1 is still readable when no journal is present. Both roles, old grants, settings/enrollment mutations and PIN cooldown publication are denied while pending. Ordinary revocation preserves the journal.

`PasscodeCore.DualPINLegacyJournal` is main-process only. The prepared plan contains the wrapped resource key and exact old/new credential fingerprints; it contains no plaintext PIN or unlocked resource key. AES-GCM binds it to the existing legacy device secret and App Group. It accepts an existing managed six-digit protected resource record; a missing, unprotected or unexpected legacy record is denied without reset/recreation. This intermediate backend prerequisite must be handled by native setup/settings integration before exposing PIN changes.

Recovery applies the exact old record or recognizes the exact already-applied new wrapping, cleans biometric tokens and requires durable AccountManager-reference acknowledgment before committing the new Core A proof. Repeated application does not rewrap the key. File, legacy write, cleanup or publication failure retains the denied journal for retry. Completion produces no user session/grant and requires a fresh standard PIN entry. Core-only `changePIN` now permits B only; A cannot diverge from protected resources through that API. The native own-PIN settings route uses a covered/detached root, current opaque request and off-main work; configured-account native acceptance remains pending. Cross-store lock order is vault then legacy; reference publication is after releasing the legacy lock and must not reenter the vault.

`PINManagementFeedback` tracks presentation only on the main thread. Exact operation
tickets prevent foreign/replayed completion from removing pending coverage or
showing an error. Inactivity clears feedback while retaining a pending worker's
coverage until its matching completion. A revision-bound successful journal
recovery may clear its own earlier failure, never a newer one. The stock lock uses
the generic update error beneath credential error/cooldown priority, and clears it
on fresh input/lock/unlock. No role, PIN, grant or unlock is carried by this status.
The 37-case hosted UI suite passed; real configured settings, slow-I/O main-thread
responsiveness and physical lifecycle/snapshot timing require the manual checks
in `INITIAL_SETUP_MANUAL_CHECKS.md`.

Verified component boundaries: 73 Mac Core cases, 74 hosted iOS Core cases and 13 hosted migration/journal cases, zero failures. Full simulator app build passed (321.521 seconds, 508 actions) with retained artifact metadata. Real legacy crypto/resource derivation runs against isolated fake Keychain storage; actual shared device Keychain, native authenticated settings/recovery and full mode transitions are not established by those tests.
